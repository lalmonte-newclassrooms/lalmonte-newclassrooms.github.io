Feature flags let us test ideas with real users, roll features out gradually, and roll them back instantly—all without redeploying code. Our goal: complete in-platform A/B testing within a weekly cycle.

Architecture

The Unleash Hierarchy

Everything in Unleash nests inside this structure:

Project

Top-level container. We have one: Roadmaps.

Environment

Isolated contexts: development, QA, production.

Feature Flag

The toggle. Enable/disable per environment with variants and constraints.

Activation Strategy

Constraints, segments, sampling and stickiness define who sees the flag. No strategy = flag off.

Key Rule

A disabled flag must always deliver the standard LTS experience. No surprises.

Step 2

Create the Flag

Create your first flag locally. Same experience on local and Enterprise:

  1. Go to Projects → default
  2. Click Add new feature flag
  3. Enter flag name (e.g., TEAME-177-brain-break)
  4. Set flag type (typically "Experiment" for A/B tests)
  5. Click Create feature flag then select your new flag
  6. Configure any constraints (optional)
  7. Add variants with weights
Workflow

Create locally first → build & test → export → send JSON to PM to import into Enterprise.

Feature Flagging Guide 14 / 32
Principles

How Feature Flagging Contains Risk

  • Conditional rendering. The default (non-flagged) experience always matches the previous platform behavior.
  • Remote configuration. Deactivate experimental features within minutes (15-second polling).
  • Causal logging. Observations tied to test conditions provide causal impact data.
  • Data safety. Mask existing data with experiments_speculative_data instead of mutating permanent tables.
  • Auto-expiry. Flags expire after 1–4 weeks. Cleanup tickets are created at inception.

    PART 03

    Code Containment & Development

    The concrete implementation of containment protocols

    Feature Flagging Guide 16 / 32
    Rules

    The Containment Rules

    DO

    • Keep ALL experiment code in /experiments/[ticket-#]/
    • Use FlagSwitch for conditional rendering
    • Record observations via GraphQL
    • Mask permanent data with speculative data
    • Pass unit tests and Prettier

    DON'T

    • Build experiment logic in shared components
    • Skip recording observations
    • Mutate non-experiment tables
    • Leave experiment code after retirement
    Feature Flagging Guide 17 / 32
    Philosophy

    Why These Rules Exist

    Containment is what makes speed safe.

    Every rule above is designed so that experiment code has exactly one blast radius: the experiment itself.

    When all logic lives in /experiments/[ticket-#]/, uses FlagSwitch for branching, writes only to speculative data, and is removed upon retirement — no experiment can touch production behavior, corrupt shared state, or leave behind technical debt.

    The rules aren't bureaucratic overhead; they're the reason we can ship fast without a safety net.

    The Guarantee

    Follow them and it is structurally impossible to break anything outside your experiment.

    Feature Flagging Guide 20 / 32
    GraphQL

    Experiment Mutations

    Two primary mutations in graphQLOperations/Experiments.ts:

    commitObservation

    • Operation: addExperimentsObservations
    • Purpose: Track discrete events
    • Semantics: INSERT — creates new record
    • Data: Simple counter (0 or 1)
    • Use: Clicks, mounts, pass/fail

    commitSpeculativeData

    • Operation: upsertExperimentsSpeculativeData
    • Purpose: Persist user state
    • Semantics: UPSERT — updates if exists
    • Data: Complex JSON payload
    • Use: Preferences, settings
    Key Difference

    Observations create a history of events — each call adds a new record. Speculative data stores current state — each call replaces the existing record.

    Example

    Putting It All Together

    import { useMutation } from 'react-relay';
import { FlagSwitch } from '../../components/FlagSwitch/FlagSwitch';
import { recordExperimentObservation } from '../../graphQLOperations/Experiments';

const BrainBreakExperiment: FC = () => {
  const { user, currentPlacement } = useBrainBreak();
  const [commitObservation] = useMutation(recordExperimentObservation);

  const handleComplete = (passed: boolean) => {
    commitObservation({
      variables: {
        input: {
          input: {
            userId: `UserNode:${user.id}`,
            flagName: 'TEAME-177-brain-break',
            variantName: currentPlacement,
            observationType: 'pass_fail',
            observation: passed ? 1 : 0,
          },
        },
      },
    });
  };

  return (
    <FlagSwitch
      flagId="TEAME-177-brain-break"
      default={<StandardExperience onComplete={handleComplete} />}
      conditions={{
        control: <StandardExperience onComplete={handleComplete} />,
        treatment: <BrainBreakExperience onComplete={handleComplete} />,
      }}
    />
  );
};

    Feature Flagging Guide 24 / 32
    Process

    Accelerated QA

    Ensure experiments don't break non-experimental parts of the experience.

    TESTS

    • Default (flag-off) behavior works
    • Automated regression suites pass
    • Non-experimental functionality unaffected

    SKIP

    • Usability of experimental feature
    • Correct experiment activation
    • Feature completeness
    Lean on Automation

    Short-cycle QA leans heavily on continually-updated automated test suites for regression testing.

    Feature Flagging Guide 28 / 32
    End of Life

    Flag Retirement & LTS Conversion

    Experiment Succeeded → LTS

    1. Remove experimental code
    2. Rebuild for LTS (start fresh)
    3. Update FE automation testing
    4. Release under LTS flag
    5. Monitor 3 months
    6. Remove LTS flag
    7. Archive & document

    Experiment Failed → Cleanup

    1. Remove experiment code
    2. Remove all flag references
    3. Archive flag in Unleash
    4. Document learnings
    No Zombie Flags

    If a flag has served its purpose, retire it. Every flag retires.
